# 工具运行器与伊机控现场取帧一致性修复

日期：2026-10-09。范围仅为固定 EasyCon 1.6.4-a 的工具兼容运行器；此前暂停的母本同步仍暂停。

## 问题及修复边界

同一份入场时差脚本在伊机控 GUI 中正常、在工具中误判，不能直接归因于母本的 `WAIT 100` 或标签阈值。固定源码中，GUI 的 `CaptureService.BuildExternalGetters` 会在识图调用时锁住采集卡并执行 `GetMatFrame()`；旧工具运行器则克隆后台已经发布的缓存。后者可能在100ms等待后仍使用等待前的空白框。

另一个诊断缺陷是：旧运行器在识图结束后读取“最新帧号/时间”，后台可能已经发布更新的画面。因此这个帧号不一定属于参与匹配的截图，不能拿它来精确推断延迟。

本次不修改任何母本、IL标签、匹配算法、向上取整、`WAIT 100`、`HP > 90` / `空白 > 96` 门槛、精灵检测回退、手柄动作或 Seed/帧校准。也没有连接 Switch 进行实机验收。

## 实现

- `tools/runner_capture/SynchronizedFrameSource.cs` 是实际发布程序集使用的共享读帧入口。脚本标签、OCR、后台排空都从同一采集卡读取，禁止并行调用底层 `VideoCapture.Read`。
- 每次标签/OCR调用都排队执行一次新的 `GetMatFrame()`，不把已有监视缓存作为匹配输入。所有竞争读取使用同一异步等待队列取得许可，再同步读帧，防止后台循环抢占已经排队的脚本请求。
- 后台排空继续运行；每次成功读取都更新监视缓存。监视窗口和故障快照仍克隆缓存，不额外打开采集卡。调用者拥有匹配帧，后台的新帧不会释放或改变它。
- 分数、截图、序号和读帧完成时间绑定到同一个 `CapturedFrame`，不再在匹配后补取一个可能属于新画面的序号。
- 空帧标签返回0，与GUI一致；OCR沿用原来的空帧结果。驱动读取失败不回退旧缓存，保留错误；排队时可以取消。无法保证中断驱动内部已经阻塞的原生读取，既有进程树停止兜底继续有效。

新补丁标识为 `easycon164a-synchronous-capture-v11-stage-log-filter-input-state-v2`，基础commit仍为 `9c86137c7e63bff842175470895727a5fa9bab52`。程序集保留历史文件名 `EasyCon2.CLI.PreviewV5.exe`，文件名不是补丁版本；实际版本由 `build-manifest.json` 和程序集摘要识别。

本机CLI DLL为100352字节，SHA-256 `21f53a5d9f220a8122865374d951d01147a21e31b155ad72a7a2ed3d4d624563`；设备DLL仍为59904字节、SHA-256 `5e315514976c3e4715edec688f7a1c5322f6274b70e353eaed9feab33620c4c7`。这次没有改写串口发送实现。

## 构建、验证及生效

`tools/build_easycon164a_compat_runner.ps1` 先构建新目录，验证版本、真实发布的设备协议和取帧实现，再切换当前运行库；检测到当前运行器还在使用时拒绝切换，不结束用户进程。旧目录保留为 `*.before-synchronous-capture-时间戳`，失败不删除原运行库。

验证包括：

- 真实发布程序集上的20项原生断言与400次并发串行读取：新标签/OCR不复用缓存、元数据一致、帧归属、空帧、驱动/发布错误、排队取消、连续后台读取不抢占脚本。
- 普通遭遇模拟：缓存空白分数100，100ms后的现场分数53；保留相同96门槛，证明新读取不会把旧空白帧当成当前画面。此为可重复的软件夹具，不是采集卡实测结果。
- 原有16条真实设备程序集序列化样本以及HTTP、PRINT、Qt只读按键回显验证，确保不破坏手柄浮窗、监视与停止协议。
- 最终89项Python/Qt定向回归通过（50.728秒），原始164a的独立观察脚本 `format` 与完整绑定编译通过；具体输出保存在本机 `.tmp/runner-capture-20261009/`。初期测试命令缺少模块/误用系统Python及检查器模式缓存的问题日志保留，不计入最终通过结果。检查器的生产DLL模式与CI源码模式现使用独立构建目录，交替四次运行均通过，避免切换模式后复用错误的依赖清单。
- GitHub Actions另设无硬件原生检查，直接链接构建器复制的生产读帧源；本机集成检查则加载实际发布程序集，并核对程序集摘要，不仅测试一份独立重写代码。

当前本机源码工具已使用新运行库。关闭后重新启动源码工具即可生效，已有脚本无需仅为本次运行器修复而重新生成；正在运行的旧进程不会被原地更新。已发布绿色包不会因源码改动自动变化，本次不打包、不发布Release。

## 同脚本、同目标 A/B 验证

只读源脚本：`tools/test_scripts/entry_timing_probe.ecs`。本机已准备可直接打开的工程：

```text
D:\Codex\火叶乱数\frlg-auto-rng\runtime\script_tests\entry-timing-probe-20261009\main.ecs
```

工程只复制当前母本的三张入场标签，不发送任何按键、不改存档。它保留100ms等待及母本门槛，并限制最多400次观察；如果开始时已经出现HP栏，则退出，不用过期的起点下结论。其他设备可新建独立目录，复制源脚本为 `main.ecs`，并复制三张 `三代路闪遇敌/三代路闪HP检测/三代路闪wild检测.IL` 到同目录 `ImgLabel`。

1. 在伊机控GUI与工具高级脚本测试页分别选择同一个 `main.ecs`；工具选“正式工具兼容运行器”，不是原始CLI。
2. 使用同一采集卡、同一视频后端/分辨率、同一种宝可梦和同一组标签；两个程序轮流使用采集卡，不同时运行。
3. 从遇敌前运行观察脚本，再手动触发遭遇。先比较已知普通目标，再比较已知闪光目标，保留完整输出和现场录像。
4. `TIMING_RESULT` 仅是入场时差观察，不替代母本最终出闪确认。普通目标不应稳定误报；重复实测才可确认这个设备上的问题已消失。

诊断模式 `--verbose` 额外输出 `FRLG_CAPTURE_SAMPLE`，含实际标签、序号、`READ_MS` 和 `AGE_MS`。`READ_MS` 是软件读帧开始到返回，不含排队；`AGE_MS` 从读帧返回到诊断输出，包含匹配/监督处理。两者均不是摄像头曝光时间，不证明驱动内部没有缓冲，也不能仅凭总耗时106ms/140ms断言33ms帧差。默认不输出逐标签诊断，避免普通运行日志与时序受额外大量输出影响。
