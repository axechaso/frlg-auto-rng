# 设备标签诊断与覆盖

不同采集卡、HDMI 转换链、色彩范围和缩放设置可能让同一正确画面的 EasyCon 标签分数略有差异。本工具在“运行日志”页提供设备标签诊断和覆盖层，用于定位并替换当前采集设备上不稳定的 `.IL` 标签。

## 使用方法

1. 点击“检测端口/采集卡”，在采集卡下拉框中选择实际设备。设备档案按设备名称保存，不使用可能随插拔变化的序号。
2. 正常运行一次脚本。日志页会持续分析 HOME_BUFFER、孵蛋重启、游戏设置、池塘冲浪/战斗和 SID 神奇糖果等已经输出分数的阶段。
3. 若一个标签反复低于脚本门槛，诊断表会显示疑似标签名、最高分、门槛、连续次数和出错阶段。低于门槛不多的单次结果会立即提示；差距较大的结果须连续出现三次，避免把偶发转场帧误判成坏标签。
4. 在 EasyCon 中按正确画面重做该标签，文件名和 `searchMethod` 保持不变。
5. 可点击“选择标签文件（可多选）”、选择一个包含多个标签的文件夹，或把多个 `.IL`/文件夹拖入日志页的框中。
6. 重新搜索/生成方案。覆盖层只会复制到新生成的运行工程，原始 2.0、TID 和 SID 标签包不会被修改。

拖放依赖 `tkinterdnd2`。源码安装器和绿色版构建都会包含它；若手工精简 Python 环境导致该组件缺失，多文件和文件夹选择仍然可用。

## 指纹与安全边界

设备覆盖不依赖高级模式，也不会把整个标签语料的指纹检查关闭。顺序固定为：

1. 生成器先检查原始 2.0 或 TID/SID 标签包；
2. 原包通过后复制成独立运行工程；
3. 只把当前设备档案中、与原语料同名且 `searchMethod` 相同的标签覆盖到运行工程；
4. `label-overrides.json` 同时记录原始语料指纹、覆盖后语料指纹、设备名称和每个覆盖文件的 SHA-256；`plan.json` 也保存同一登记；
5. 运行前预检要求原始语料指纹仍是项目登记的审计值，并要求标签数量、方法分布、覆盖后总指纹和逐文件指纹全部吻合。

因此以下情况仍会阻止启动：

- 原始标签包本身不是已审计版本；
- 导入了原语料中不存在的文件名；
- 重做标签改变了 `searchMethod`；
- `.IL` 不是有效 JSON、图像数据损坏或坐标字段不完整；
- 覆盖应用后又手工修改运行工程中的标签或登记文件；
- 把一个设备档案叠加到另一个已经覆盖且未重新生成的工程。

合法覆盖会在预检提示中显示“已应用设备标签覆盖……原始标签包指纹仍已验证”，不会要求开启“高级模式（所有指纹仅警告）”。

## 文件位置与清理

设备档案保存在：

```text
%LOCALAPPDATA%\FRLG-Auto-RNG\device_label_overrides\<设备名称哈希>\
```

每个档案包含 `manifest.json` 和 `ImgLabel\`。生成工程中的覆盖登记为相邻的 `label-overrides.json`。点击“清除当前设备覆盖”只删除当前设备档案；原始标签包和已保存的其他设备档案不受影响。清除或重新导入后，当前方案会失效，必须重新生成。

诊断是基于脚本已经打印的标签分数，不会擅自降低门槛或自动制作新标签。能力值、等级、性格等旧流程若只输出“某组识图失败”而没有逐标签分数，工具只能提示标签组，不能可靠指定组内某一个文件。
