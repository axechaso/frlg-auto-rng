# 六项新功能修复与三项体验增强方案

日期：2026-10-03。基线：`1f4f7ec`，工具版本 `0.9.4.2`。

状态：**2026-10-03 已按用户“实施”授权完成代码和本地兼容运行器修复。复验与待实机项见[实施复验报告](../../acceptance/2026-10-03-six-feature-implementation.md)。下文保留原方案，涉及“只写方案”的句子描述当时的编写范围。**

依据：[六项新功能验收报告](../../acceptance/2026-10-03-six-feature-review.md)。在原六项验收修复基础上，追加用户要求的历史日志页性能、标签故障修复弹窗和逐页功能引导。本轮仍只更新方案。

## 1. 目标和边界

本次应修好四个已复现缺陷，并处理一个过期测试基线；新增三项体验增强见第 6–8 节：

| 优先级 | 问题 | 影响 | 修复完成标准 |
| --- | --- | --- | --- |
| P1 | SID 目标事件生成时缺少字符串拼接符，实际输出末尾多一个引号 | 野生和定点 SID 遍历都不能消费该结果 | 生成的 PRINT 经真实运行器执行后符合协议 |
| P1 | SID 解析器不接受真实日志的 ANSI、时间戳前缀 | 正确结果也会被判为缺少证明 | 原始运行日志直接交给解析器即可判断，不需用户清洗 |
| P1 | 运行器用 `byte[]` 输出摇杆坐标，JSON 实际是 Base64 | 整条状态被拒绝，虚拟手柄和日志操作卡都无法回显 | 实际 HTTP 响应包含整数数组，直接通过 Python 校验 |
| P2 | 更新预校准在按钮成为可勾选控件前设置默认值 | 无配置文件的首次启动仍关闭 | 真正全新目录首次启动开启；用户明确关闭则继续保留 |
| P2 | 母本同步后，标签阶段测试仍断言旧语料摘要 | 全量回归有一项失败 | 重新核对已审计资产，更新独立测试基线后全量通过 |
| P2 | 进入历史日志页卡顿 | 切页、筛选和预览阻塞界面 | 后台发现日志、缓存列表、按需限量预览；性能指标单独复验 |
| P2 | 标签报错后只有日志和折叠卡片，修复路径不明显 | 用户不知道修哪个标签、如何验证生效 | 故障归因提示、自动去重弹窗、分步修复、原目标重建形成闭环 |
| P2 | 各页面缺少完整功能引导 | 新用户不知道必要输入、顺序和运行边界 | 全部 8 个侧栏页及相关设置入口有可恢复的中文分步引导 |

以下边界不变：

- 只维护 PySide6，不恢复旧 Tk 文件。
- 不顺带改变 Seed/F1/F2、HOME_BUFFER、孵蛋菜单、识图阈值、SID ADV 遍历顺序或校准算法。
- 不覆盖用户母本、标签覆盖、存档、TID 实测表、预校准记录和遍历进度。
- 保留高级模式的指纹仅警告约定，不借本次修复重新收紧指纹策略。
- 滚轮切档、神秘礼物字段和有效奇偶方案已通过本次离线检查，本轮以回归为主，不重写。
- 运行期间的浮窗只能观察，不新增串口连接，不另开采集卡，不用日志猜按键。
- 定点支持仍按真实路线白名单。`Gift` 类别目前被明确拒绝；伊布、拉普拉斯、波克比等不能在本次修复中直接全量放行。

## 2. 第一部分：修通 SID 结果生成与解析

主要文件：`automation/target_verification.py`、`run_sid_traversal.py`、`tests/test_target_verification.py`、`tests/test_sid_traversal.py`。

### 2.1 修正生成语句，不放宽结果协议

`_event_line()` 当前生成的尾部相当于：

```text
... "|SHINY=" & 1|END=1"
```

改为正确的 ECS 字符串拼接：

```text
... "|SHINY=" & 1 & "|END=1"
```

实施要求：

1. `SHINY=0`、`SHINY=1` 两条 TARGET 分支分别覆盖，不只检查其中一条。
2. 验证 `NON_TARGET_SHINY` 和 `INCOMPLETE` 两类原有语句仍正确。
3. 继续只在 Seed、Advance、物种同时命中的分支生成 TARGET 证据；不能在第一次看到闪光标签时直接确认 SID。
4. 保留唯一锚点和身份校验，不能用全局替换引号的方式修补整份 ECS。
5. EasyCon `format` 通过只作为语法检查。必须执行生成的 PRINT，并断言实际终态行以 `|END=1` 结束，没有多余引号。

### 2.2 只规范化已知日志包装，再严格解析

在 `target_verification.py` 内增加不依赖 Qt 的纯函数处理日志行，按以下顺序工作：

1. 去除 EasyCon 输出的合法 ANSI 颜色码。
2. 处理行首空白；如文件首存在 BOM，只处理文件首 BOM。
3. 接受裸协议行，或者去除行首一个合法的 `[HH:mm:ss.fff]` 时间戳及其后空白。
4. 对剩下的完整协议行执行原有字段、版本、身份及结束标记校验。

必须保持以下拒绝行为：

- 错误 `RUN` / `ATTEMPT`，未知事件或版本，非法布尔字段，缺少 `END=1`，多余尾引号，不完整行，重复终态标记均不能成为成功证据。
- 不在任意一句话中搜索 `SIDTRAVERSAL|` 子串；例如被普通日志引用的协议文本不应视为真实终态。
- 不删除任意字符直到正则匹配，不自动“修好”历史错误标记，不把“出闪”“抓获成功”等普通文本当作证明。
- 保留原始日志文件及现有日志显示行为，不把整个日志写入链路改成清洗后的文本。

两个 SID 修复必须一起交付：只去时间戳仍会被末尾引号阻断，只修引号仍会被时间戳阻断。

### 2.3 已生成工程与断点兼容

当前注入器看到同一身份的 V1 注入标记会直接返回原脚本，因此只修 `_event_line()` 不足以处理旧工程。

- 将注入实现标记升级为 `# SIDTRAVERSAL_TARGET_VERIFICATION_V2`；日志线协议仍为 `SIDTRAVERSAL|V=1`，不混淆实现版本和通信版本。
- 当前实现只对 V2 标记进行幂等复用；`validate_injected_target_verification()` 要检查新标记和预期事件语句，不能只数身份字段。
- 遇到 V1 注入工程，明确提示“该方案使用旧版结果标记，请重新生成后继续”，不在旧脚本上重复叠加注入。
- 重新生成的是当前候选的运行工程，不清空 SID 遍历记录，不改变候选位置，不把旧候选误记为已验证非闪。
- 恢复时若原有上下文一致性校验不允许直接续跑，应说明差异并保留断点，不能为了兼容绕过校验或静默重置到起点。
- 历史日志只供查看。旧的畸形终态不追认成功，不追溯推进候选。

### 2.4 终态复验

| 输入证据 | 应有行为 |
| --- | --- |
| 本轮目标 Seed、Advance、物种命中，目标闪光 | 确认当前候选 SID，记录本轮结果 |
| 同样精确命中，但目标非闪 | 只排除当前候选一次，按既有规则推进 |
| 非目标闪光 | 保留现场并按现有非目标闪光策略暂停，不确认、不排除当前候选 |
| 证据缺失、不完整、重复或身份不符 | 暂停并保留当前候选，不偷跳下一项 |
| 用户停止、运行器错误、搜索超限 | 沿用现有停止/暂停规则，不能因协议修复变成自动排除 |

除解析结果外，还要断言 worker 的状态文件、当前候选和计数，防止“解析通过但错误推进”。

## 3. 第二部分：修正真实运行器的按键状态 JSON

主要文件：`tools/patches/`、`tools/build_easycon164a_compat_runner.ps1`、`automation/easycon118.py`、`pyside_app/run_input_state.py` 及对应测试。

### 3.1 修发送端，保持严格接收端

当前 `System.Text.Json` 将 `byte[]` 序列化为字符串，例如 `"gIA="`。期望契约是：

```json
{
  "buttons": ["A"],
  "hat": "CENTER",
  "left_stick": [128, 128],
  "right_stick": [255, 0]
}
```

实施方案：

- 将输出 DTO 的 `LeftStick`、`RightStick` 改为 `int[]`，在投影为 DTO 时明确生成两个整数；设备内部报告仍保留原来的字节格式。
- 最新快照和历史事件使用同一个转换函数，不能只修 `snapshot` 而漏掉 `events[].snapshot`。
- 保留通信协议版本 1：这是修复原协议的错误实现，不是引入新格式。
- Python 继续要求长度为 2、整数且范围为 0–255；Base64、字符串数字、布尔值、越界值仍拒绝。
- 失败时显示状态不可用并清除观察高亮，保留文本日志；不伪装成设备正常且没有按键，也不停止正常脚本。

### 3.2 可重放补丁、构建缓存和交付一致性

采用新增纠错补丁的方式，保留原 v1 补丁历史：

1. 新增 `tools/patches/easycon164a-input-state-json-v2.patch`，在现有输入状态及视频解耦补丁之后应用。
2. 默认构建源码目录改为新的 `.build/easycon164a-input-state-v2-source`，从锁定提交 `9c86137c7e63bff842175470895727a5fa9bab52` 重放整套补丁；不删除旧构建目录。
3. 构建脚本增加对纠错补丁的独立检测，验证 DTO 类型确实是整数数组。现有“文件/接口存在就算应用成功”的检查不能代替这一检查。
4. 补丁应用前先 `git apply --check`；未知或部分应用状态应报出文件差异，不用宽松替换继续构建。
5. 构建身份升级为 `easycon164a-label-supervision-v10-stage-log-filter-input-state-v2`，同步 `EXPECTED_COMPAT_PATCH_ID`、构建 manifest 和测试。
6. 在暂存输出中先做真实 HTTP、版本和协议验收，再替换工具使用的运行器。发现旧运行器正在运行时不覆盖；提示用户停止后再更新。
7. 成套更新运行器相关文件，不只复制 EXE。至少对 `EasyCon.Device.dll`、`EasyCon2.CLI.PreviewV5.dll` 增加 manifest 摘要和一致性验证；EXE 是 apphost，仅核对 EXE 摘要不能证明 DLL 已更新。
8. 新增 DLL 指纹检查沿用现有高级模式的告警策略；缺文件、协议不受支持等结构问题仍明确报错，不与“仅警告”混为一谈。

旧运行器不能因为 EXE 可启动就继续宣称支持按键回显。若版本不匹配，提示重建/更新兼容运行器；用户主动选择原始后端时，继续明确显示该后端不提供回显，不偷偷替换后端。

### 3.3 运行时行为不变

- 不改设备报告顺序、按住时长、自动松开、连接/断开和重启命令。
- 不在控制线程内增加 JSON 序列化、网络等待或 GUI 调用。
- 日志操作卡与手柄继续共用现有状态客户端，不各自建轮询器。
- 验证停止、进程瞬退、失联、会话切换时清除旧高亮；旧会话晚到的数据不能显示到新阶段。
- 短按键可以在“最近操作”记录显示，但不能为追求可见性把“当前按住”伪造为持续按住。
- 打开、关闭、拖动观察窗均不得向串口发按键或释放命令。

### 3.4 必须分开的三层测试

1. **真实 C# 序列化**：用重建后的实际程序集直接调用状态缓冲的发布/读取接口，再序列化结果。覆盖 A/B、组合键、方向、摇杆边界、松开和历史事件；不打开串口。
2. **真实 HTTP 接口**：启动暂存运行器，`--port mock`，脚本仅 PRINT/WAIT，不启用视频，读取 `/capabilities` 和 `/input-state`，把原始响应直接交给生产 Python 解析器。
3. **真实 GUI 接线**：把上述真实序列化样本送入正式窗口的接收路径，检查浮窗和日志卡同时正确渲染，以及结束/失联状态。

当前 `MockGamePad` 不发布真实设备报告，所以第 2 层只能证明服务和快照格式，不能证明实机按键提交链路。第 1 层验证状态转换，第 3 层验证界面；设备实际操作回显须另做用户确认的实机检查。

## 4. 第三部分：修复首次默认值与按钮文字

主要文件：`pyside_preview.py`、`pyside_app/window.py` 及 PySide6 测试。

### 4.1 初始化顺序

统一顺序为：创建按钮 → `setCheckable(True)` → 连接状态文字刷新 → 设置默认值。

- 更新预校准默认 `true`；出闪录像默认 `true`。
- 低分自适应、标签故障保护等其他开关保持现有默认值。
- 原有用户明确保存的 `false` 优先于默认值，不能借更新强制重新打开。
- 不连带修改命令行、旧计划的默认语义；本轮修复的是正式 GUI 首次启动行为。

### 4.2 配置恢复与显示一致

增加小型状态显示辅助函数，使用固定基础标题和当前 `isChecked()` 渲染文字。正常点击和 `QSignalBlocker` 下恢复配置后均调用它。

- 不依赖被屏蔽的 `toggled` 信号刷新文字。
- 不通过来回切换开关制造信号，以免触发方案失效或写盘副作用。
- 不从已经带 `✓` 的标题继续拼接，避免多次恢复变成多个勾。
- 保留严格布尔值检查与损坏配置保护；无效配置不能被关闭窗口自动覆盖。

### 4.3 首次与重启测试矩阵

| 配置状态 | 预校准 / 录像 | 额外断言 |
| --- | --- | --- |
| 数据目录全新，设置文件完全不存在 | 开 / 开 | 文字与状态一致，收集请求为 true |
| 已有 `{}`，或分别缺少其中一项 | 缺省项为开 | 不影响其他已有设置 |
| 两项明确为 `false` | 关 / 关 | 关闭再启动仍为关 |
| 两项明确为 `true` | 开 / 开 | 勾选文字不重复、不丢失 |
| 一开一关 | 精确保留 | 不能按一个总开关覆盖另一项 |
| 非法类型或损坏 JSON | 明确提示并保留原文件 | 不把字符串 `"false"` 当作开启，不自动重写 |

每个用例使用独立临时数据目录；“无文件”用例执行前明确断言文件不存在。现有诊断探针固定子目录不宜直接当永久回归，否则上轮保存的配置会掩盖首次启动错误。

## 5. 第四部分：更新测试基线并补齐 CI

### 5.1 母本摘要重新核对

当前唯一全量测试失败来自 `tests/test_label_wait_stages.py` 的旧摘要。实施时重新核对磁盘实际内容，而不是直接相信本文件数字。

本次验收证据：

- 源语料：33 文件，2,105,553 字节，SHA-256 `abedc36a98710f02b02b79f0af10f6221e3e0a04f3f0f6e107d5c9887ce2661e`。
- 导入缓存：33 文件，2,106,377 字节，SHA-256 `2cd606b7d04c3517b250680858ebf1ef3b042aef18685608775345b073b7d94f`。
- 旧测试仍期待缓存 `04a0cdda…`；当前实际缓存与 manifest、已支持集合一致。

完成来源和物化差异核对后更新测试固定基线，保留“实际文件 → 摘要 → 审计基线/manifest”的独立比较。不能把 expected 直接设为本轮 computed 值让断言恒真，不能跳过失败测试，也不能回退用户新脚本去满足旧断言。

本轮没有新的脚本同步授权，不主动从外部目录导入另一批更新；若实施时资产已再次变化，记录差异后确认应采用的基线。

### 5.2 修复现有测试的盲区

当前 CI 使用显式测试名单，而非自动发现所有模块。把以下已存在模块加入 `.github/workflows/ci.yml`，新加的测试模块也必须登记：

- `tests.test_target_verification`
- `tests.test_sid_traversal_policy`
- `tests.test_run_input_state`
- `tests.test_frame_parity`

新增回归不能只有手写“理想数据”：

- SID：实际生成语句 → 实际 CLI 输出 → 原始日志解析 → worker 终态。
- 输入状态：真实 .NET JSON → Python 校验 → 两个显示控件。
- GUI 默认值：正式 `CompleteWindow` + 独立目录，不能只检查预览窗口或空 JSON。

建议新增一个独立 .NET 9 协议测试 job：从版本控制的补丁重建相关状态源文件，编译真实 DTO/状态实现并输出测试 JSON，再由 Python 生产解析器验证。不得另写一份“正确 DTO”替代被测实现；所需枚举来自同一锁定源码，并验证来源。此 job 不连接设备，也不依赖用户的母本标签。

完整兼容运行器构建和真实 HTTP/PRINT 往返作为本地交付必过项；CI 中缺少资产或原生构建环境时要明确标记未执行，不能用纯 Python 测试替代后写“已通过”。依赖本机审计母本的测试仍与仓库无关测试分层，不强迫公开 CI 读取用户路径。

## 6. 新增一：解决历史日志页卡顿

### 6.1 已确认的代码风险与待测内容

当前 `CompleteWindow.select_page("history_logs")` 直接调用 `refresh_history_logs()`，随后在 GUI 线程完成目录扫描、排序、表格重建和选中日志读取。

已从代码确认：

- `pyside_app/log_history.py:discover_logs()` 分别递归扫描 `runtime/pyside6` 和父级 `runtime`；最终按文件去重，但子目录遍历工作已经重复发生。
- 当前递归会进入运行工程的标签等非日志子目录，工程越多，目录枚举越重。
- `filter_history_logs()` 每次输入搜索文本都会重新创建整张 `QTableWidget` 的单元格；选中变化又可能触发预览读取。
- `history_log_details()` 在 GUI 线程读文件、去 ANSI 并一次性 `setPlainText()`，默认末尾预览可达 4 MiB。
- `read_log_preview()` 先读取大小、定位后使用无参数 `read()`；对持续增长文件，读取量并没有被严格限定在最初预算内。

这些是明确的阻塞路径，不等于已经量化了用户机器上每项的占比。实施前先记录扫描耗时、文件/目录数、模型更新耗时、预览读取和文本排版耗时，不用猜测代替性能基线。

### 6.2 页面立即显示，扫描与筛选独立于运行任务

新增 `HistoryLogController`，建议放在 `pyside_app/history_controller.py`，独立管理扫描任务、预览任务和缓存。不能占用现有代表搜索/设备操作的 `window.job`，否则看历史日志会误禁用脚本控制。

1. 进入页面先显示现有缓存或空态和“正在读取历史日志…”，将扫描调度到后台；不等待扫描结束才完成切页。
2. 复用 `pyside_app/jobs.py` 的线程交付方式，必要时封装专用只读 worker；后台只处理文件和普通数据，不触碰 QWidget、QPixmap 或 QTextDocument。
3. 每类请求有递增 request ID 和取消标记。再次刷新合并/取消旧扫描，旧结果不得覆盖新路径、新筛选或新选择。
4. 离开页面取消未开始的预览和无用结果投递；正在运行的扫描可协作取消。窗口关闭时安全收尾，不能强杀线程或向已销毁控件发送结果。
5. 扫描、筛选、预览任务分别限流；频繁点击刷新不能不断创建线程。后台异常显示在本页，不覆盖当前脚本的运行状态。

### 6.3 去重扫描、缓存和增量更新

- 扫描前规范化根目录并合并父子覆盖：`runtime` 已包含 `runtime/pyside6` 时只遍历一次，同时保留旧版日志与用户日志归档根。
- 使用可取消的目录枚举，跳过明确不存放运行日志的资源子目录（例如工程 `ImgLabel`）；不通过任意固定深度排除 SID/TID 嵌套子流程日志。
- 不跟随符号链接、目录联接等重解析目录造成循环；逐项处理权限不足、删除和文件轮转，单个目录失败不能清空所有结果。
- 每个文件复用一次取得的 stat 元数据，缓存规范路径、流程、大小、修改时间和检索文本；不为建立列表读取整份日志。
- 第一版使用内存索引即可，不引入数据库。缓存按规范化的输出/用户根目录隔离，切换数据目录后必须失效，不能显示上一个数据目录的结果。
- 返回页面先使用缓存；建议缓存新鲜期 30 秒，过期后台刷新。手动刷新始终能触发扫描；运行结束时优先加入本次已知日志路径并标记需增量刷新。
- 筛选输入防抖约 150–200 ms，基于缓存过滤，不再次扫描磁盘。大集合过滤和排序也放到 worker，最终只把索引结果交给 GUI。
- 保留当前选中文件、排序和滚动位置；文件消失则显示“文件已移动或删除”，不能悄悄预览另一份日志。

### 6.4 表格与预览限制

将历史页改为 `QTableView + QAbstractTableModel`，建议模型放在 `pyside_app/history_model.py`。保留现有列、双击/打开文件与文件夹功能，避免为每条日志创建五个 `QTableWidgetItem`。

- 数据分批提交，每批建议不超过 200–500 行；模型更新只在 GUI 线程做，批次间让出事件循环。不在每批后重置选择或重新读取同一日志。
- 未完成扫描时明确显示“已发现 N 项，扫描中”；扫描结束后再给出完整总数，不能把第一批当作全部结果。
- 默认预览末尾最多 256 KiB 且最多约 3,000 行，实际 `read()` 必须显式传入长度上限，解码、截行和 ANSI 清理在后台完成。
- 显示“当前仅预览末尾，可加载更多或打开原文件”。“加载更多”按块读取，内嵌预览总量建议上限 1 MiB；完整内容通过打开原文件查看，不隐藏原日志。
- 预览请求绑定规范路径及请求 ID，缓存键包含大小/修改时间；快速连点 A、B 日志后，A 的慢结果不能盖住 B。
- 对正在写入的日志只获取有界快照，不长持有独占句柄、不阻止运行器追加；文件缩短、轮转、UTF-8 半字符和 ANSI 半序列都应安全处理。
- 清理历史工程、删除日志不是本项解决方案，不能以删用户数据换速度。

### 6.5 性能与正确性验收

使用独立测试目录生成 5,000 份跨流程日志、多个嵌套工程，以及 100 MiB 级的大日志和持续追加日志；另做权限失败、旧目录、重叠根和联接目录场景。不得拿用户真实目录做破坏性基准。

以下为验收目标，不是本轮测量结果：

- 本地 SSD 基准环境，切页到可交互空态/缓存不超过约 200 ms；暖缓存返回不触发同步扫描。
- 用 16 ms Qt 心跳记录 GUI 响应：扫描/筛选/预览期间延迟 P95 目标小于 100 ms，避免出现超过 250 ms 的单次主线程阻塞；记录机器和样本量后比较修前/修后。
- 预览读取字节数不随日志文件总大小增长，100 MiB 日志不得被完整读进内存；输入搜索不增加目录枚举次数。
- 快速切页、搜索、刷新、关闭窗口时无串结果、无崩溃；原日志字节内容不变。
- 运行脚本时进入历史页，停止按钮、实时输出和按键回显继续响应。

自动化 CI 主要断言线程归属、取消、去重、读取上限和扫描调用次数；墙钟性能以单独基准记录，不把不同 CI 机器速度误判为功能回归。

## 7. 新增二：标签错误自动弹窗并引导修复

### 7.1 复用已有能力，不另造标签系统

已有 `LabelIncidentStore`、`Accessories.poll_incidents()`、`LabelEditorDialog`、原生同图/三张新帧验证、设备覆盖和同目标重建。当前缺口主要在：错误出现后用户只看到日志或折叠卡片，缺少明确、连续的修复指引。

新增故障提示协调器和修复向导，建议分别为 `pyside_app/label_repair_prompt.py`、`pyside_app/label_repair_guide.py`。编辑、测试、保存与恢复仍调用已有实现，不复制一套覆盖文件和验证算法。

### 7.2 什么情况弹窗

| 来源 / 状态 | 提示与处理 |
| --- | --- |
| 当前运行产生完整故障事件，安全停止码为 20 | 确认脚本已结束/输入安全锁定后，自动显示一次修复弹窗 |
| 预检发现具体标签缺失、损坏或范围非法 | 尚未启动脚本即可弹窗，列出文件和修复入口 |
| 故障保护关闭，但日志明确报告最终识别失败 | 结束后显示“可能存在标签/页面问题”的诊断弹窗；证据不足处标为未知 |
| 正常匹配候选低分、正在自动重试、瞬时页面过渡 | 不弹窗、不改变现有重试或停止逻辑 |
| 采集无画面/帧不更新 | 弹窗先引导检查视频源和占用，不直接要求重做标签 |
| 未登记阶段或用户自选脚本只有“长时间没输出” | 不武断判定标签故障；提供查看日志/启用故障保护的说明，不能承诺总能发现卡死 |

弹窗提示默认启用，与“标签故障保护”是两个概念。保护开关默认关闭的既有约定不变；不开保护时无法获得的截图、分数、阶段信息应如实说明，不能伪造完整事件。

去重与身份要求：

- 以故障事件 ID 和运行身份去重，同一事件只自动提示一次；多个失败标签合并到一个弹窗，不能连环弹出。
- 仅当前运行及其明确登记的子阶段事件可自动弹窗。当前 `poll_incidents()` 找不到运行匹配时会回退到历史首项，这个回退可用于历史卡片，但不能直接作为自动弹窗依据。
- 事件写入与退出回调先后不确定时，做有界异步重试等待完整事件；不得把半写入文件当作完整证据，也不得在 GUI 线程等待。
- 旧的未修复事件在用户主动打开故障列表时展示，不在每次启动或切页时当作新故障弹出。
- “稍后处理”保留事件和可见入口；运行中若只能安全展示非模态提醒，编辑入口须等运行/设备任务结束，不抢占设备。

### 7.3 弹窗内容与第一步判断

弹窗先回答四个问题：哪个流程/阶段失败、哪些标签参与判断、实际分数与判定条件是什么、下一步应该检查什么。

- 显示实际 ROM 语言、机型、采集卡名称、实际分辨率、标签来源/覆盖状态和故障时截图。
- 分数必须带比较符，例如“94，要求 ≥95”；缺失值显示“未采集”，不能填 0。
- OR/AND 候选组按实际条件展示，不能因为某个本应不匹配的候选分数低就标成坏标签；不能直接把最高分候选称为正确结果。
- 优先核对当时页面是否正确、是否已稳定、语言/分辨率是否一致。错误页面或旧画面应引导修复启动位置/采集设置，不把错误页面制作成正确标签。
- 保留“开始修复”“查看完整日志”“稍后处理”三个入口；缺原图/原标签时说明不能直接编辑的原因，提供补采集/导入入口。
- 故障信息按纯文本显示，不执行或自动打开日志、标签内容中携带的命令/链接。

### 7.4 修复向导闭环

1. **确认现场**：展示故障截图与应处界面的说明，用户确认是预期页面，或转入设备/页面检查。不得自动向主机发键寻找页面。
2. **选择待修标签**：默认聚焦事件涉及的候选，保留用户选择；展示当次实际加载标签，不能误用另一设备的最新标签替代。
3. **编辑或导入**：复用现有标签编辑器的模板和搜索范围框选，也可选择/批量拖入 `.IL`。批量文件逐项校验、测试和显示冲突，不能一个通过就把整批标成已验证。
4. **原图验证**：调用固定 EasyCon 原生匹配，展示分数、阈值和搜索位置；只通过原图还不能认定修复完成。
5. **三张新帧验证**：复用现有兼容预览通道，在同设备、同分辨率、同标签摘要条件下测试三张新帧；没有可用通道时引导用户启动已有预览服务，不另开采集卡争用。
6. **排除误匹配**：对容易混淆的 HOME/退出/相邻页面提供负样本检查；没有负样本时明确标为未验证，不暗示已排除所有误判。
7. **保存到当前设备**：展示覆盖范围和修改摘要，经用户确认后事务保存并保留上一版；原始母本不改，其他设备不受影响。
8. **应用与复测**：使用原已选目标重建工程并正常预检，成功后显示“覆盖已应用，待运行复测”；仅用户点击开始后运行，不自动重新搜索另一个目标、不自动重启游戏。

保存草稿、保存覆盖、工程已应用和实机已验证是不同状态。当前 `Accessories.finish_loaded_incidents()` 以正常退出推定解决的逻辑需一并收紧：退出码 0 不足以证明原失败阶段已通过；应绑定相同覆盖摘要及原故障阶段的成功证据。没有证据时保持“待复测”，或记录明确的用户人工确认来源。

标签方案及画面变化后，旧验证结果失效。设备、分辨率、搜索方法、模板/范围/阈值任一变更，必须重新测试；重建失败保留草稿与覆盖历史，不误显示为已解决。

不新增“报错就自动降阈值”行为。HOME_BUFFER 已有低分自适应仍按原开关和规则工作；其他识别不受该向导影响。高级模式的指纹仅警告约定保持不变，但损坏文件、未知结构、跨设备验证等安全校验不能被当作指纹告警略过。

### 7.5 验收重点

- 同一事件被轮询和退出回调同时发现时，只弹一次；旧事件和别的运行不误弹。
- 保护开启/关闭、原始后端、预检失败、正常重试、正常低分候选、采集故障分别测试，不能只测退出码 20。
- 弹窗打开/关闭/稍后处理不会发送按键，也不会自动保存或重新启动脚本。
- 缺截图、缺标签备份、只读目录、测试失败、用户取消、设备切换、批量文件局部失败均有明确分支。
- 修复完成后，同目标、同设备的新工程实际加载覆盖标签；其他设备、原母本和用户存档未改变。
