## 2. 已核实的现状

### 2.1 颜色问题的来源

`pyside_preview.py` 中 `APP_STYLE` 为 `quickToggle` 和 `advancedToggle` 使用白色/透明底，选中后仅变成浅色 `#E9EDFF`。QQ 通知和共通设置沿用普通 `ghost` 按钮，视觉层次不足。

`quickToggle` 还被“重新检测”“虚拟手柄”“监视窗口”和出闪后处理开关复用。因此不能直接把整个 `quickToggle` 样式换成饱和色，否则会改到截图之外的控件。

现有开关开启时有 `✓` 前缀；高级“设置”在高级模式关闭时不可用。两项交互应保留，不能只通过颜色表达状态。

## 4. 界面实现方式

### 4.1 在已有对象上增加样式属性

在 `pyside_preview.py` 的控件创建处设置静态动态属性，例如：

```python
button.setProperty("emphasis", "true")
button.setProperty("accent", "blue")  # blue / green / violet / amber
button.setProperty("emphasisRole", "toggle")  # toggle / action / segment
```

仅给第 1 节列出的七个控件添加属性。保留 `kind`、对象引用和原有 objectName，特别是 `qqNotificationButton`，避免影响现有逻辑和测试定位。

在现有 `APP_STYLE` 通用规则之后，追加受上述属性约束的 QSS。使用明确的 `:enabled`、`:checked`、`:hover`、`:pressed`、`:focus`、`:disabled` 组合，禁用规则不能被后面的选中/悬停规则盖掉。

高级分组保持一体化的左右圆角及中间分隔线。可以为 `advancedControl` 单独设紫色边框，但不得覆盖到其他 `QFrame`。

### 4.2 避免样式和状态分叉

- 调用现有 `setChecked()`、`setEnabled()` 后由 Qt 自动呈现状态，不再新增持久化字段。
- 继续使用当前 toggle 回调添加/移除 `✓`；检查配置恢复、孵蛋全部配置导入和运行结束后的启用恢复。
- `pyside_app/window.py` 和 `migration.py` 只承担验收与必要接线核对，单纯配色不应重写这些业务流程。
- 不给每个按钮零散调用整段 `setStyleSheet()`，防止它覆盖全局禁用和焦点样式。
- `quickToggle` 的其他使用者维持原样。

### 4.3 布局验收

检查 1920×1080、1360×840、1280×800，以及 Windows 100%、125%、150% 缩放下的显示；尤其检查 `✓ 命中后更新预校准` 的完整文字。

现有宽/窄布局切换阈值为 1320，QQ 入口在宽度小于 980 时已有隐藏规则。本轮不改变这两项响应式策略；应验证临界宽度附近没有新增重叠或截断。

若必须微调尺寸来容纳原有文字，优先调整左右内边距和最小宽度，保持原有换行布局；不要直接扩大整行固定宽度。

## 5. 脚本同步实现步骤

### 步骤 A：固定输入快照并列差异

1. 记录实施时的 Git HEAD、原包 33 文件指纹、完整标签指纹、OCR 模型指纹及三个变化文件的单文件摘要。
2. 对原包与缓存进行逐文件比较，不仅看 `asset_manifest.json`。
3. 本文指纹只代表 2026-09-30 的核对结果；实施时若原包继续变化，应重新审计新增差异，不能按旧指纹覆盖用户新内容。
4. 在独立暂存目录验证迁移与生成；不要改动正在运行的工程，也不要批量清理现有 `.tmp/`、工具 `bin/obj` 或历史日志。

### 步骤 B：同步最新快捷登记逻辑

1. 从正式入口提取最新版快捷目标选择和登记函数，更新 `shortcut_registration_main.ecs`。时间轴入口使用相同动作，但保留准确的阶段日志来源名称。
2. 从 `lib/27_孵蛋测试流程.ecs` 提取最新版自行车登记函数，更新 `shortcut_registration_egg.ecs`。
3. 同步 `egg_settings_retry.ecs` 中的设置入口及相关等待，保留其有限识别重试、正确保存设置和故障阶段记录。
4. 更新 Python 中的 Options/孵蛋入口迁移常量及对应转换函数。最新版输入应原样保留已更新的动作；确认为旧版的目标片段才进行迁移。
5. 对旧版、最新版分别保留精确锚点；目标函数缺失、重复或结构未知时给出明确错误，不做全文件盲目替换。
6. 同一输入连续转换两次，第二次不得产生新增动作、重复函数或重复阶段标记。

重点保留最新原包的以下变化：

- 主菜单与重要道具列表不再通过连续多次 UP“顶到顶部”。
- 从已知起点进入背包、从首项选择第 1/2/3 项。
- 快捷登记成功和失败返回路径中的 `B → WAIT 1500`。
- 孵蛋登记完成后到 Options 的 3 次 DOWN。
- 主入口当前的 Options 导航及御三家分支。

**必须单独验证的分支：**快捷目标位为 0 时登记函数直接返回，未必经历背包导航。不能仅凭“最新版普通分支是 3 次 DOWN”就推断所有调用起点都相同；实施时应核对调用前的已知光标，并分别验收“未检查快捷位、检查后无需修改、实际完成登记、御三家”四条路径。此处若需要额外修正，须先用动作序列或实机日志证明起点，不能再引入猜测性连按。

## 9. TID 流程 SID 验证成功后创建存档

### 9.1 用户看到的行为

TID → 御三家流程完成 SID 验证、工作进程结束并释放设备后，自动打开标题为“创建存档”的窗口，进入**新建草稿**状态。该行为覆盖普通目标 TID/SID、按实际身份接续的穷举流程，以及第 10 节的新模式；不是只服务于 6V 闪 SID。

用户可以修改名称和其他信息，点击“保存”才写入存档配置。取消或直接关闭窗口不新增、不修改存档；已有日志和成功报告仍保留。此处创建的是工具中的存档资料，不代表再次在游戏内执行保存操作。

预填字段及来源：

| 字段 | 唯一数据来源 |
| --- | --- |
| 存档名称 | 根据本轮游戏版本、主角名称和实际 TID 生成建议名，例如“叶绿-Leo-12345”；重名时追加序号 |
| 游戏版本 | 本轮 TID 连续计划中的火红/叶绿，不读取此时工具顶部旧存档 |
| ROM 语言 / 地区 | 本轮实际使用的英文/日文母本及请求快照 |
| 主机 | 本轮运行的 Switch 1/2 |
| TID | 最终成功尝试中识别、确认的 TID；不能回填最初的目标输入框或另一轮观测值 |
| SID | 最终成功尝试使用、并通过御三家闪光验证的候选 SID；不能使用穷举阶段最初的固定 F3 SID |

TID/SID 显示为五位十进制，`00000` 是合法值，不能被空值判断排除。主角名称可以用于建议名和报告，但现有 `SaveProfile` 没有独立的主角名/性别字段，本轮不为此无关扩展存档格式。

验证口径必须准确：游戏界面并未直接读取 SID；工具的 SID 来源仍是 TID 生成链和运行计划，御三家出闪用于验证。单次闪光判定不能区分同一闪光组中低三位不同的 8 个 SID，因此报告记录“通过闪光验证的候选 SID”，不声称 OCR 读到了精确 SID。界面继续采用现有流程的候选 SID，不擅自换成同组最小值。

### 10.2 6V 闪 SID 的含义与 PID 来源

复用当前“6V 闪 SID”功能：以 TID 和“6V 闪 PID”计算让该 PID 闪光的 SID。默认沿用现有 `7942EF72`，高级模式允许使用用户已填的合法 PID，并在生成计划时冻结该值，不能运行到一半再从界面读取。

这是“建立可让对应 6V PID 闪光的身份”，不等于本次用于验证 SID 的御三家必然是 6V。目前御三家验证搜索不强制 6V；继续选取符合现有验证条件、可执行的闪光目标。若以后要求验证用御三家也必须 6V，那是另一项搜索约束，不能混进本功能造成长时间无结果。

| 3. 搜索 6V 闪 SID | 从该 TID 的 8 个闪 SID 中选择最早可执行的一次出现 | 找到 SID/ADV，F3 等待合法，生成计划通过预检 |
| 4. 重新建档定向乱数 | 使用锁定 TID 及参数，新建子计划定向取得该 TID/目标 SID | TID 正确命中，目标 SID 阶段完成 |
| 5. 御三家验证 | 复用研究所桥接、御三家生成与既有 SID 修正重试 | 最终目标命中且闪光；否则按现有重试半径处理 |
| 6. 完成与创建存档 | 写入本轮成功报告，进程退出后预填第 9 节窗口 | 用户点击保存后新增工具存档资料 |

关键区别：第一轮穷举结束时 SID 已经由固定 F3 产生，不能在原存档上“填一个新 SID”就算完成。新模式必须在锁定 TID 后重新建档执行 SID 乱数，不能直接沿用目前 `resolve_exhaustive_starter_plan()` 的“读取固定 F3 的 SID → 搜索御三家”路径。

### 10.4 只接收真正通过去噪的 TID

现有任意 TID 交接代码已检查 `$denoise_hit_count >= $denoise_need_hit`，但输出标记只有 `MATCH/TID/SID_ADV`，不足以复现成功的参数点。扩展交接快照时应在原有去噪成功分支一次性输出：

- 实际 TID、完整数字识别状态、去噪实际命中次数和要求次数。
- 本次成功点的 OP/F1/F2 **归一化乱数中心帧**，以及需要沿用的 select 补偿参数。
- 当前语言、机型、主角名/性别、声音/按键/Seed Button 等设置。
- 本轮实际固定延迟、OP 修正、SID ADV 修正及模板来源摘要。
- 观察点/尝试标识和完整记录边界，避免把上轮 TID 与下轮帧数拼成一个结果。

只能接受这次连续流程中明确的去噪成功快照。TID 实测表中的普通一条观测、多条重复历史记录、不同参数点碰巧识别到同一 TID，都不能代替去噪成功。

帧数转换复用现有穷举到乱数的归一化规则和校准结果，不把穷举检查点里的原始偏移直接填进乱数模式。NS1/NS2 的 OP 模型偏移、固定延迟和修正只应用一次，避免重现“穷举得到的 F1 用到乱数模式就过小”的问题。

TID 实测表继续只记录其现有 TID/参数/设备上下文，不新增 SID 表。阶段快照与 SID 计划放在本次连续流程的状态和报告文件中。

### 10.5 SID 搜索、可达性和选择顺序

复用 `rng/sid_reverse.py` 的现有算法，不新写另一套 TID→SID 生成链：

1. 用锁定的 TID、PID 算出 8 个满足第三世代闪光异或条件的 SID。
2. 用本轮 F3 固定延迟、英文/日文前缀及 SID ADV 修正，通过 `sid_min_advances_for_f3()` 求最小可执行 ADV。
3. 通过 `find_earliest_shiny_sid()` 在现有搜索上限内遍历 TID 生成链，选择 **ADV 最小的可执行出现位置**，不是 SID 数字最小者；默认复用现有上限 1,000,000 ADV。
4. 将选中的 `SID + ADV + PID + 最小可执行 ADV + 参数快照` 一并保存。SID ADV 沿用现有零基定义，不额外加 1。
5. 提供进度和取消；到上限无结果时明确停止在规划阶段并保留已去噪 TID，不能悄悄改回普通任意 SID 流程。

必须处理同一个 SID 在链上多次出现的问题：`build_tid_starter_flow_plan()` 当前会调用不带最小 ADV 的 `first_sid_advances()`。新功能不能选中了后一个可执行出现位置，生成时却重新退回前面不可执行的位置。应让派生计划显式携带已选 ADV，或统一用相同的可执行下界重新解析；计划、母本 F3 等待、日志与最终报告必须一致。

不改为随机 F3。新的定向阶段使用指定目标 SID/ADV 对应的等待，原先移除 F3 随机模式的决定保持不变。

### 10.6 派生计划与 SID 验证重试

在独立子目录生成派生计划，保留原穷举计划与证据，不覆盖当前运行工程。使用不可变请求副本切换到“乱数模式”，填入去噪 TID、选定目标 SID 和归一化 OP/F1/F2；关闭派生请求的任意 TID 接续、特殊号码筛选及固定 F3 身份推断，保留原游戏/语言/机型、校准、设备标签覆盖和运行设置。

初次复现使用锁定的成功中心点，不继续推进穷举坐标，不选另一个 TID。不要直接修改用户界面中的穷举参数或保存选项；界面仍保留原配置，日志和本轮状态显示当前正在定向乱数。

优先接入现有目标 SID 流程和 `run_flow_attempts()`，不复制第二套研究所、御三家和停止控制。派生计划必须保留“出发点是已去噪任意 TID”的来源，便于结果回填和续跑，但其执行语义是固定 TID/目标 SID。

目标命中但不闪时，复用既定 SID ADV 修正顺序：相对初始修正 `0、+2、-2、+4、-4……`，同奇偶范围测试完后再试 `+1、-1、+3、-3……`。不要改成单向一直减 2，也不要把不同修正的结果混写成同一尝试。

每次修正后复核 F3 可执行下界与目标 SID 的出现位置；若原 ADV 不再可执行，只能明确重新选取**同一目标 SID**的合法出现位置并更新计划，或说明失败。不能静默换成穷举阶段 SID、无关 SID 或另一个 TID。御三家目标和最终报告应对应本次实际采用的候选，成功修正继续沿用现有自动回填机制。

### 10.7 请求、持久化与停止恢复

建议为 `TidStarterFlowRequest` 增加默认关闭的 `any_tid_sixv_sid` 和冻结的 `shiny_sid_pid`，连同校验、JSON 读写、固定延迟后重建、计划摘要和测试一起更新。命名可按实际实现微调，但不能只改 GUI 而漏掉工作进程或校准后的新计划。

`FormReader.flow()` 负责读取新选项和 PID；`TidState` 保存/恢复选项。把去噪开关也加入 `_refresh_tid_controls()` 的联动触发源；新开关同时纳入运行中锁定、参数变化使计划失效的机制。“接近目标区间后自动转乱数”是另一项现有功能，不能当作本模式的开关，任意 TID 下继续遵守已有互斥规则。

为这个多阶段任务保存带版本的阶段状态：尚未锁定 TID、已锁定待规划、已生成定向 SID 计划、当前修正尝试、已验证完成。状态记录运行上下文/模板摘要并原子写入；与当前参数或模板不兼容时明确拒绝自动续用，不静默采用旧结果。

停止与恢复遵守以下规则：

- 每个计算和子进程启动边界检查停止标志；停止后不得再开始新一轮建档。
- 未获得去噪成功快照时，沿用原穷举续跑机制。
- 已锁定 TID 后保留身份和派生计划，下次续跑不能重新穷举并换一个 TID。
- 游戏内执行到一半的阶段，不能仅凭本地状态跳过并声称已完成；从该阶段安全的现有启动点重做，沿用工具启动确认。
- 监视窗口和停止按钮由现有连续流程统一管理，不因新增中间 Python 计算阶段而失效；设备逐阶段释放，不同时启动两个 EasyCon。
- 搜索无结果、预检失败、识图故障、SID 重试用尽分别保留明确原因；失败或停止均不弹创建存档窗口。

## 11. 新增 TID 功能验收与回归

### 11.1 无硬件自动化用例

在已有 `tests/test_tid_starter_flow.py`、`test_tid_starter_runner.py`、`test_tid_calibration.py`、`test_tid_session.py`、`test_sid_reverse.py`、`test_save_profiles.py` 及 PySide6 测试中补充行为用例；新增测试模块仅在现有文件确实不适合时拆分。

重点用例：

1. **开关条件**：四项前提全满足才可用；分别关闭任一项会取消并禁用；旧配置缺字段默认关闭；保存恢复后状态一致，后端拒绝非法组合。
2. **去噪快照**：有效 TID、完整识别、去噪达标且参数点一致才接续；缺帧数、混合观察点、未去噪的实测记录、截断日志均不允许生成定向计划。
3. **参数复现**：英/日、NS1/NS2、开启/关闭固定延迟检测；穷举成功帧归一化后回填，不重复减机型偏移，不使用界面原始起点代替成功点。
4. **SID 搜索**：8 个候选都满足 PID 闪光条件；按最早可执行 ADV 排序；重复出现的 SID 跳过不可执行的早期位置；语言与修正影响下界；ADV 零基一致；无结果/取消不执行后续脚本。复用现有 TID=24、PID=`7942EF72`、英文 F3=14900 的测试样本核对最早可执行位置。
5. **完整顺序**：使用假的 `FlowRunner` 证明“穷举去噪 → SID 规划 → 重新建档定向乱数 → 研究所 → 御三家验证 → 成功报告”；不能少一次定向 SID 阶段就直接进入御三家。
6. **SID 重试**：同奇偶正负交替优先；始终保持锁定 TID 和 6V 闪 SID 目标；修正后 ADV、等待、御三家计划与报告一致，不能复用上一次尝试身份。
7. **成功回填**：普通目标 SID、延后身份解析和新模式都覆盖；使用最终运行游戏/语言/机型/TID/候选 SID，而非当前顶部存档或旧文本框；合法 0 值正常显示。
8. **不应弹窗的情形**：仅 TID 命中、只生成 `resolved_identity.json`、目标非闪、非目标闪光、退出码 0 但故障、手动停止、报告不完整、旧 run_id、窗口关闭；全部不得自动创建草稿。
9. **保存保护**：预填确为新建；关闭草稿没有写入；重名不覆盖；保存失败保留草稿；保存成功新增并选中；重复完成事件只弹一次；不破坏已打开窗口的未保存编辑。
10. **续跑与周边行为**：停止阶段边界不会再启新进程；锁定后恢复不换 TID；校准后的请求不丢开关/PID；标签保护开/关均可匹配报告；监视和 QQ 通知正常，整轮成功只通知一次。

### 11.2 生成、实机及最终交付

在第 6 节的生成矩阵中增加英/日 × NS1/NS2 的新模式工程，核对实际 F3 等待和成功标记，再对代表工程使用真实 EasyCon `format` 检查。仍不把通过语法检查写成已经刷到 6V 闪光。

实机重点是一条完整的“去噪任意 TID → 定向 SID → 御三家验证 → 新建存档”链，确认第二次建档确实复现同一 TID，以及弹窗中的信息与最终报告一致；SID 失败重试、停止续跑另列验证。当前没有已完成的实机结果，本方案不预先承诺通过。

交接文档必须写清新模式四个前提、默认关闭、会再次新建游戏、默认 6V 闪 PID、同奇偶优先的修正规则、阶段续跑位置，以及“验证用御三家不强制 6V”的边界。最终执行时将本节用例和前述脚本/配色回归一起检查，再按第 8 节约定提交和触发 Actions。
