# Windows 绿色版整包更新器设计

日期：2026-08-30

目标仓库：`axechaso/frlg-auto-rng`

目标运行形态：PyInstaller `onedir` Windows 绿色版

## 目标

为绿色版增加无需 GitHub 登录的整包自更新能力。程序启动后在后台检查公开仓库的正式 GitHub Release；发现新版时只提示，用户明确确认后才下载。更新过程必须校验完整性、避免运行中替换、失败时恢复旧版，并且不能改动 `%LOCALAPPDATA%\FRLG-Auto-RNG` 内的用户资料。

本功能仅在冻结打包版中启用。源码运行模式继续由 Git 管理，不提供自更新。

## 非目标

- 不做增量补丁；每次下载完整绿色版 ZIP。
- 不更新正在运行的 EasyCon 流程。
- 不把 GitHub Token、发布凭据或私钥放进客户端。
- 不把 Seed 表更新并入整包更新；现有 Seed 表更新器保持独立。
- 不承诺防御 GitHub 仓库发布凭据本身被攻破；SHA-256 用于发现下载损坏和错误资产。
- 首版不提供测试版频道、强制更新或后台静默安装。

## 用户体验

1. 主窗口正常打开，不等待网络。
2. 冻结版在后台检查更新；同一版本每 24 小时最多自动检查一次。
3. 无更新、网络不可用或 GitHub 限流时不弹错误框，只在更新状态处保留可读结果。
4. 发现新版时显示非阻塞提示，包含当前版本、新版本、发布日期、文件大小和简短更新说明。
5. 只有用户点击“下载并安装”后才开始下载。公共工具区另保留“检查程序更新”按钮，允许绕过 24 小时缓存手动检查。
6. 下载过程显示进度，并允许在进入安装阶段前取消。
7. EasyCon、搜索、设备检测或其他后台任务正在运行时禁止安装，并提示先结束当前任务。
8. 安装成功后自动启动新版；失败则恢复旧版并显示日志位置。

## 版本与 Release 合同

主程序增加两个构建常量：

- `APP_VERSION`：显示版本，例如 `1.1.9`；
- `APP_VERSION_CODE`：严格递增整数，例如 `2026083001`，用于可靠比较。

更新源固定为公开仓库 `axechaso/frlg-auto-rng` 的最新正式 GitHub Release。客户端调用 GitHub Releases API，只接受非草稿、非预发布的 Release。每个可更新 Release 必须同时包含：

- 完整绿色版 ZIP；
- `update-manifest.json`；
- 人类可读 `.sha256` 文件。

`update-manifest.json` 的首版结构：

```json
{
  "schema": 1,
  "version": "1.1.9",
  "version_code": 2026083001,
  "package": "FRLG-Auto-RNG-1.1.9-windows-x64.zip",
  "sha256": "64位小写十六进制",
  "bytes": 545000000,
  "unpacked_bytes": 1400000000,
  "release_url": "https://github.com/axechaso/frlg-auto-rng/releases/tag/...",
  "notes": "本版主要更新"
}
```

客户端拒绝未知 schema、非 HTTPS 地址、其他仓库资产、文件名不匹配、版本号未递增、大小不匹配或哈希不匹配的更新。旧 Release 没有清单时视为“不支持应用内更新”，不是程序错误。

## 组件与职责

### `app_version.py`

只保存版本常量和仓库标识，供 GUI、更新客户端、打包脚本及测试共同读取。

### `app_updater.py`

负责纯逻辑和网络阶段：

- 解析并验证 Release 与更新清单；
- 比较 `version_code`；
- 使用 ETag、最后检查时间和超时控制后台检查；
- 流式下载 ZIP，实时计算 SHA-256；
- 防 ZIP 路径穿越地解压；
- 验证新目录的必要文件和内嵌版本；
- 计算磁盘空间需求；
- 写入安装请求 JSON 和更新日志。

网络仅使用 Python 标准库 HTTPS，不增加运行依赖。缓存、下载和日志位于 `%LOCALAPPDATA%\FRLG-Auto-RNG\updates`。

### `package_entry.py`

增加只供更新器验证使用的无 GUI 参数，例如 `--version-json`。它输出冻结包内的版本与 schema，不打开设备、不连接 EasyCon。

### 独立更新器

构建一个小型、独立的 `FRLG-Auto-RNG-Updater.exe`。主程序在安装前把更新器复制到用户更新目录，从那里启动，并传入安装请求文件；更新器不依赖即将被替换的 `_internal` 目录。

更新器职责：

1. 等待主程序 PID 退出；
2. 再次确认目标安装目录、暂存目录和请求文件一致；
3. 把当前安装目录重命名为同盘临时备份；
4. 把已验证的新目录重命名到原路径；
5. 确认新入口存在后启动新版；
6. 任一步失败则移回旧目录；
7. 记录结构化结果，供新版启动时展示或清理。

更新器只允许操作请求中已经规范化且通过父目录约束的两个精确目录，不接受通配符或环境变量作为删除、移动目标。

### GUI 接入

公共工具区增加当前版本、更新状态和“检查程序更新”按钮。自动检查在线程中执行，所有 Tk 控件更新通过主线程 `after()` 回调。更新操作与现有运行锁共用：程序忙时可检查，但不能下载后安装。

## 数据流与安装事务

```text
启动冻结版
  → 读取本地检查缓存
  → 后台读取 GitHub 最新正式 Release
  → 下载并验证 update-manifest.json
  → version_code 大于当前值时提示
  → 用户确认
  → 检查任务空闲、目录可写和剩余空间
  → 流式下载 ZIP 到 .part
  → 校验大小与 SHA-256 后原子改名
  → 安全解压到当前安装目录同一磁盘的隐藏暂存目录
  → 运行新版 --version-json 并核对版本
  → 写安装请求并启动临时更新器
  → 主程序正常退出
  → 更新器交换新旧目录
  → 启动新版；成功后清理暂存，旧目录按策略删除
```

配置、日志、档案、TID 进度、Seed 表和设备标签覆盖都位于 `%LOCALAPPDATA%\FRLG-Auto-RNG`，不参与目录交换。更新缓存位于其 `updates` 子目录，可单独清理。

## 空间、备份与清理

下载前按照“ZIP 大小 + 解压大小 + 安全余量”检查下载盘和安装盘。安装目录不可写或空间不足时不退出主程序，保留清晰错误。

目录交换期间只保留一个旧版备份。新版成功启动并写入健康标记后，更新器清除旧版备份；如果新版未能启动，更新器恢复旧版。异常断电留下的暂存或备份在下次启动时只做诊断提示，不未经确认递归删除不明目录。

## 错误处理

- 启动自动检查失败：静默记录，不影响使用。
- 手动检查失败：显示简短错误与日志路径。
- 下载中断：保留或删除精确的 `.part` 文件，不进入安装。
- 清单、大小、ZIP 或哈希失败：删除精确暂存文件，拒绝安装。
- 新包结构或版本验证失败：保留当前程序，拒绝退出。
- 运行任务未结束：拒绝安装。
- 交换失败：更新器执行回滚；若回滚也失败，保留新旧精确路径和人工恢复说明，不继续删除。
- 新版启动失败：恢复旧版并重启旧入口。

所有更新日志不得包含 GitHub 凭据；客户端本身不持有凭据。

## 构建与发布自动化

扩展 Windows 打包脚本，使它：

1. 从 `app_version.py` 读取版本；
2. 同时构建主程序和独立更新器；
3. 生成绿色版 ZIP；
4. 计算 ZIP 大小、解压大小和 SHA-256；
5. 生成 `update-manifest.json` 与 `.sha256`；
6. 执行冻结入口、更新器和包结构冒烟检查。

当前完整发布依赖被 Git 忽略的审计后 EasyCon、1.1.8 和 TID 本地资产，GitHub Actions 不能凭仓库内容还原发布包。首版因此新增本机发布脚本，而不在 CI 中伪造不完整构建。发布脚本必须：

1. 确认当前提交已推送且对应 CI 成功；
2. 调用上述 Windows 打包与冻结包验证；
3. 校验 tag、`APP_VERSION` 和 manifest 一致；
4. 先创建草稿 Release；
5. 上传 ZIP、manifest 和 SHA 文件并回读核对名称、大小；
6. 三项齐全后才把 Release 转为正式发布。

发布脚本使用开发者本机已有的 GitHub CLI 登录，不把凭据写入包或源码。任何失败都只留下草稿 Release，不得留下声明为可更新但资产不完整的正式 Release。未来只有在审计资产具备明确、可复现且许可允许的下载来源后，才把相同步骤迁到 GitHub Actions。

首次支持应用内更新的 Release 需要人工用旧绿色版做一次端到端验收。当前已经发布但没有 manifest 的版本不会被错误安装。

## 测试与验收

### 单元测试

- 版本比较、manifest schema 与仓库/资产约束；
- ETag/24小时缓存、超时和限流处理；
- 流式哈希、大小不符、取消和网络中断；
- ZIP 路径穿越、绝对路径、重复入口和缺文件拒绝；
- 磁盘空间计算；
- 安装请求路径规范化与越界拒绝；
- GUI 忙闲状态、线程回调和源码模式禁用；
- 更新器成功交换、各失败点回滚及健康标记清理。

### 构建检查

- 现有全部 Python、ECS 和真实 EasyCon 1.6.4-a 检查继续通过；
- 冻结主程序 `--version-json` 输出与 manifest 一致；
- 冻结更新器可在临时目录完成无硬件模拟升级；
- ZIP CRC、文件清单、大小和 SHA-256 一致；
- 本机发布脚本拒绝版本、tag、提交状态或资产不一致，并确保残缺发布保持草稿状态。

### Windows 端到端验收

在不连接采集卡和单片机的临时目录中验证：旧版发现新版、用户确认、下载、退出、目录交换、启动新版、用户数据保持、旧版清理。再分别模拟断网、哈希错误、空间不足、安装目录只读、主程序未退出、交换失败和新版无法启动。

硬件流程不是更新器验收的一部分；更新不得自动启动 EasyCon 或发送手柄输入。

## 发布与兼容策略

- 首版只检查稳定 Release；预发布版永不自动提示。
- `schema=1` 保持向后兼容；未来若必须改变安装协议，旧客户端看到不支持的 schema 时只提示手动更新。
- 现有绿色版没有更新器，必须手动安装首个带更新器的版本；从该版本开始才能应用内升级。
- 每次正式发布仍保留可人工下载的完整 ZIP，更新器不可用时用户可以手动解压到新目录。
