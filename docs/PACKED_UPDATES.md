# 少量压缩包发布与按需更新

2026-10-08：用户确认保留增量更新，将大量独立发布文件合并成少量压缩包。本次只改更新传输和发布资源生成，不改脚本、标签、搜索或实机时序，也不覆盖已发布的 v0.9.5。

## 给使用者的说明

- 程序仍是文件夹版，完整绿色版仍以 ZIP 提供。这里减少的是 GitHub/Gitee Release 上传附件数，不是将安装后的全部运行库塞进单个 EXE。
- 更新前仍比对安装目录的每个文件。未变化的文件复用；有变化、缺失或损坏的文件需要哪些小数据块，就读取哪些。
- 支持 HTTP Range 的服务器只传所需数据块，不必下载整份外层压缩包。
- 服务器不支持 Range 时，只下载包含所需数据块的相关压缩包。小脚本和标签的数据块与大型运行库分开归档，所以小改不会因此下载未变化的 DLL/OCR 模型。
- 确认框显示按需读取的预计下载量，以及整份相关压缩包回退的下载量上限。实际回退时状态和进度总量会更新，不把 Range 预计量冒充保证值。
- 已完成并校验的数据块可在中断或取消后继续复用。下载完成的外层压缩包也会缓存；未完成的文件清理掉，下次重试重新下载该文件。
- 安装仍组装完整新目录、逐文件校验、检查版本、退出后换目录，失败仍用原回滚流程。用户配置、日志、存档资料、TID/SID进度、Seed表与设备标签覆盖不参与替换。

## 发布资源

新的 `incremental-release-assets` 只含：

```text
incremental-packs.json
update-pack-<SHA256>.zip
update-pack-<SHA256>.zip
...
```

每份外层ZIP不超过90 MiB，内部是已压缩的 `update-data-<SHA256>.bin`。外层用ZIP_STORED不重复压缩，以便按精确偏移读取；内部块仍使用有界zlib。大文件仍独立切成最多16 MiB原始内容的块。新构建将小型文本/脚本/IL标签和小型二进制运行库分开，各用16个稳定路径桶，再分开归档，避免小运行库也被带入标签的小更新。旧资源转换只换外层格式、完全保留原块摘要；新构建分组有调整，但旧缓存中与新清单大小/摘要相同的块仍可复用，大文件分块规则不变。

`gitee-release-assets` 另含不变的 `gitee-update-manifest.json` 与完整ZIP的90 MiB分卷，服务旧客户端。GitHub/Gitee使用同一份合并增量清单和相同压缩包；自动跨源下载仍要求版本、完整包摘要、增量清单完全相同，手动源不跨源。

新构建由 `tools/create_update_manifest.py` 自动生成合并格式；`tools/verify_incremental_release.py` 逐文件核对完整ZIP，返回精确上传名单。发布脚本仅上传该名单，不上传内部106个独立块，不靠通配符拾取旧目录。

用0.9.5 r4完整程序验收新分组时，Gitee附件从113个降为13个：6份增量ZIP、1份增量清单、5个旧客户端整包分卷、1份整包清单。标签/脚本/文本资源独立ZIP约12.3 MiB，二进制运行库另归档；每个附件均不超过90 MiB。附件数随今后程序内容变化，不固定写死为13。935项回归及资源逐文件验收通过，但这份参考包未包含本次新更新器，不用于新版本发布。

需要把已有旧格式资源转换为**新的验收目录**时可运行：

```powershell
.\.venv\Scripts\python.exe -m tools.pack_incremental_release `
  --package '<完整绿色版.zip>' `
  --manifest '<update-manifest.json>' `
  --assets-dir '<旧incremental-release-assets>' `
  --output-dir '<新的incremental-release-assets>' `
  --gitee-output-dir '<新的gitee-release-assets>'
```

输出目录必须不存在，且不能与源目录重叠。该命令先验证旧资源，再生成、验证合并资源，重新切分旧客户端整包分卷；不修改源目录、不删除旧发布文件、不上传或发布。

若要从已有完整程序目录验收新构建的资源隔离规则，将 `--assets-dir` 替换成 `--unpacked-root '<完整程序目录>'`；此模式会重新生成内层块。旧混合小块不能仅靠套外层ZIP就变成纯标签块，因此两种验收方式的附件数量可能不同，均须逐文件核对完整ZIP。

## 旧客户端升级

- 旧更新器只查找 `incremental-manifest.json`，不认识新的 `incremental-packs.json`；新发布目录不再放旧增量清单。旧客户端因此走其原有完整ZIP/分卷升级，不会因读到schema 2而报错。
- 完整更新清单仍为schema 1，独立安装器/版本探针/回滚合同不变。安装包含本次更新器的新版本后，后续更新才使用合并资源的按需读取。
- 新更新器也能读取历史schema 1独立小包，以及只有整包清单的历史Release。发现新合并清单损坏、缺包或不一致时明确报错，不暗中降级绕过校验。
- 不单独用合并Gitee资源替换已发布版本的旧格式镜像：这会破坏两源清单一致性。下一次正式发布必须提高版本号和版本码，并在两源使用相同资产格式。当前v0.9.5线上资产保持原样。

## 校验与边界

schema 2保留原文件、块、SHA-256与解压大小字段，新增压缩包列表和块位置表。只接受按摘要命名、大小不超过90 MiB的压缩包；每个块仅登记一次，必须在包内且不重叠，禁止未引用的压缩包。制作及发布验收检查真实ZIP成员、存储方式、偏移、块内容和完整绿色版的逐文件内容。

Range请求使用 `Accept-Encoding: identity`；206响应必须有完全一致的 `Content-Range`、数据长度和块SHA-256。无Range的200响应按整包大小/摘要验证后才登记缓存。400/405/416/501表示Range不可用时只重试同一URL的普通GET；403、网络和证书失败仍按既有指定源/自动回退规则处理。错误206、错误摘要、额外编码或多余字节不是“服务器不支持Range”，不能借机绕过校验。

缓存盘空间按可能的整份压缩包回退及物化后的块预留，不只按小Range的预计量计算。正常运行不向更新源上传资料。本协议不解决更新源自身的API403，也不关闭TLS验证。
